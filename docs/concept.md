# 核心概念

本文解释本技能的设计动因与关键术语。读完后应能理解「为什么这样设计」，从而在扩展或调整时做出不违背设计意图的改动。

## 为什么是「静态白盒」

审计手段可沿两个轴分类：

| | 黑盒 | 白盒 |
|---|------|------|
| **静态** | 只发请求看响应（不现实） | **只读代码推理** ← 本技能 |
| **动态** | 渗透测试、模糊测试 | 插桩调试、运行时污点追踪 |

本技能选择**静态白盒**，原因是：

1. **零门槛**：目标仓库只要有源码就能审，不需要能编译、能跑起来、能连数据库
2. **零风险**：不执行任何目标代码，不会污染数据、不会打崩服务、不会触发真实攻击行为
3. **零依赖**：不装任何外部工具，避免「环境没有 Semgrep 就审不了」的脆弱性
4. **覆盖面广**：动态测试只能覆盖被执行到的路径，静态阅读可以覆盖全部代码

**代价**：无法证明漏洞可达。这是必须接受的权衡，也是「置信度」字段存在的原因。

## 污点源与污点汇

审计数据流类漏洞的核心模型：

```
污点源（Source）  →  传播（Propagation）  →  污点汇（Sink）
   外部输入              赋值/拼接/传递          敏感操作
```

### 污点源

凡是**外部可控**的数据都算，不只是 HTTP 参数：

- HTTP：Query / Body / Path / Header / Cookie / Multipart 文件名
- 消息队列的消息体、第三方回调、Webhook
- 上传文件的内容与文件名
- 环境变量、启动参数、配置文件中的外部可写项
- 数据库中已被污染的历史数据（二次注入）

### 污点汇

数据到达后会**产生安全后果**的地方：

| 汇 | 后果 |
|----|------|
| SQL 执行 | 数据泄露、绕过认证、写入 |
| 命令执行 | 服务器接管 |
| 代码/表达式求值 | 服务器接管 |
| 反序列化 | 服务器接管 |
| 文件系统操作 | 任意文件读写 |
| HTTP 客户端 | SSRF，内网穿透 |
| 模板渲染 | 服务端模板注入 |
| 重定向 | 开放重定向、钓鱼 |
| 日志 | 日志注入、敏感信息落盘 |

**只有「源可达 + 汇危险」同时成立才是漏洞。** 中间任何一环断开，都不成立。

## 有效拦截与无效拦截

这是最影响误报率的判断。常见误区是「代码里有过滤就安全」。

### 视为有效

- 预编译语句 + 参数绑定（`PreparedStatement` 占位符、ORM 参数化）
- 命令执行使用数组参数且不经 shell（`ProcessBuilder(List)`、`execFile`、无 `shell=True`）
- **严格白名单枚举**后拼接（如排序字段只允许 `[id, name, created_at]`）
- 框架级自动转义（MyBatis 的 `#{}` 而非 `${}`）
- 类型强约束（参数被解析为整数后再使用）

### 不视为有效

- 手工转义（`StringEscapeUtils`、`replace("'", "''")`、`addslashes`）
- 黑名单过滤（可用大小写、注释、编码、Unicode 归一化绕过）
- 仅前端 JS 校验
- `strip_tags` 单独使用
- **部分链路上做了校验**——Sink 是公共方法，其他入口可能绕过校验直接调用
- 正则只过滤了少数字符（如只挡单引号）

判定时必须在 `description` 中说明「为何可被绕过」，而不是简单写「过滤不充分」。

## 严重等级 ≠ 置信度

两个正交维度，容易混淆：

| | 含义 | 取值 |
|---|------|------|
| **严重等级（severity）** | 假设漏洞成立，危害有多大 | Critical / High / Medium / Low / Info |
| **置信度（confidence）** | 我们有多确定漏洞真的成立 | 高 / 中 / 低 |

组合示例：

- 「生产数据库口令硬编码」→ 危害极大（Critical）、证据确凿（高）
- 「某处拼接疑似进入 SQL，但该 DAO 方法可能未被路由调用」→ 危害大（High）、但不确定可达（低）

**低置信度不等于低风险**，它只表示需要人工确认。这类条目在报告中标注 `needs_manual_review: true`，并在 HTML 中用虚线边框 + 「待人工确认」提示区分。

置信度系数直接影响风险分（高 1.0 / 中 0.7 / 低 0.4），所以「不确定」会自然降低总分——这是刻意设计，避免堆积大量猜测抬高风险等级。

## 根因合并与去重

同一个根因在多处出现时**必须合并为一条 finding**，用 `occurrences` 列出全部位置。

为什么重要：

- 一个不安全工具函数被 20 处调用 → 报 20 条会让报告失去可读性
- 更严重的是**虚高风险分**（20 × 15 = 300，封顶后直接严重级）
- 修复动作也是同一个（改那一个函数），拆开报没有额外价值

判断标准：**修复动作是否相同**。同一个修复动作 → 合并。

## 唯一事实源

报告产出遵循「JSON 是唯一事实源」：

```
security-audit-report.json   ← 所有结论只在这里定义一次
        ↓ 渲染（不新增、不修改内容）
security-audit-report.html
```

禁止的做法：

- 先写 HTML，再从 HTML 反推 JSON
- 两边分别维护内容，靠人工保证一致
- HTML 中包含 JSON 里没有的发现

这条原则的价值在于**可校验**：拿 JSON 能复算风险分、能跑脚本比对、能接入其他系统。若 HTML 是事实源，一切自动化都无从谈起。

## fail-open 与 fail-closed

安全校验的异常处理方向：

| 模式 | 行为 | 安全性 |
|------|------|--------|
| fail-open | 校验出错时**放行** | ✗ 危险 |
| fail-closed | 校验出错时**拒绝** | ✓ 正确 |

典型 fail-open 写法：

```java
try {
    return authService.check(token);
} catch (Exception e) {
    return true;   // ← 异常时放行，攻击者只需构造让校验抛异常的条件
}
```

或更隐蔽的兜底默认值：

```java
boolean allowed = config.getBoolean("security.strict", true);  // 配置读取失败 → 返回默认允许
```

判定要点：**不要只看有没有 catch，要看 catch 之后的控制流。** 吞掉异常本身不可怕，吞掉异常后继续执行敏感操作才是漏洞。

## 纵深防御的审计视角

同一个风险点应在上多层被拦截。审计时若发现某一层缺失，要判断其他层是否补上：

```
网络层：WAF / 限流 / IP 白名单
   ↓
网关层：鉴权 / 路由白名单 / 安全响应头
   ↓
应用层：权限中间件 / 参数校验 / 序列化隔离
   ↓
数据层：参数化查询 / 归属过滤 / 加密存储
   ↓
运行层：最小权限 / 只读文件系统 / 网络策略
```

「单点缺失但其他层覆盖」→ 降级为加固建议（Info/Low）。「多层同时缺失」→ 提升等级。

这也是为什么 `file-network`（SSRF）与 `config-infra`（网络策略）要排在 P1 前列——它们是上面几层的补位检查。

## 边界与局限的显式声明

静态审计必然有盲区，**不声明盲区比有盲区更危险**——读者会误以为报告覆盖了全部。

因此：

- 未纳入的目录 → `scope.excluded` + 理由
- 未运行的维度 → `dimension_coverage` 中 `checked: false` + 原因
- 分析方法的固有局限 → `limitations` 数组（必填，不可为空）

典型的 `limitations` 条目：

```
本次为纯静态白盒审计，未执行目标代码，也未做动态验证，漏洞可达性需人工确认。
未执行依赖漏洞库比对，组件版本影响性结论需结合官方安全公告复核。
仓库 git 历史未纳入分析，无法确认凭证是否已通过历史提交泄露。
```

## 术语速查

| 术语 | 含义 |
|------|------|
| 白盒静态审计 | 只读源码推理，不执行目标代码 |
| 污点源（Source） | 外部可控的输入 |
| 污点汇（Sink） | 到达后产生安全后果的操作 |
| 攻击链（attack_chain） | 从源到汇的完整路径描述 |
| 根因合并 | 同一修复动作的多处问题合并为一条 finding |
| fail-open | 校验异常时放行 |
| 唯一事实源 | JSON 是报告内容的唯一定义处 |
| 维度标识 | 报告中使用的维度唯一 ID，如 `authn-authz` |
| 深度模式 | 快扫 / 标准 / 深度，决定维度覆盖面与追踪精细度 |
| 拦截措施 | 参数校验、参数化、转义、权限中间件等 |
